# Gaming Contracts — Actually Need Server-Side PDF Signature or an E-Signature Platform

The decisive trade-off is control of the authorization ceremony. If a game backend already knows who may approve a publishing, licensing, or tournament contract, and it only needs to seal the final PDF plus retain a trustworthy audit record, a server-side digital-signature path can fit. If people must review, consent, delegate, decline, receive reminders, or prove how they were authenticated, the system needs a signing workflow, not merely a signed file. **Choose from the evidence the contract process must preserve, then choose the machinery.**

TL;DR: use a cryptographic PDF signature when the server is the signer and your team owns identity, authorization, key custody, retention, and verification. Use an e-signature workflow when a human signing ceremony is part of the requirement. For a mixed gaming contract flow, keep business authorization and the immutable audit event in your own domain, then treat PDF sealing or an external ceremony as replaceable execution paths.

## What failed before a signature was even applied?

Consider a bounded production scenario: a studio service generates the final licensing contract after legal and finance approvals. The contract is revision 17, its SHA-256 digest has been recorded, and a release job is ready to seal it. Between approval and sealing, however, another process regenerates the PDF with corrected metadata. Both files look equivalent to a reviewer, but the bytes differ. Signing the second file produces a valid cryptographic result for the wrong revision.

The invariant is narrow: the bytes authorized must be the bytes signed, and the audit record must bind the contract ID, revision, digest, authorization decision, signer role, signing method, and resulting artifact. A green verification indicator cannot recover an authorization link that the application never recorded.

Bytes first.

This is where I start the design review: identify the evidence boundary before discussing libraries or services. I would reject a design that sends a mutable document identifier to a background worker and later asks that worker to fetch "the latest" PDF. The queue message should carry an immutable revision and digest; the worker should fail closed if regenerated bytes do not match. No retry should silently switch revisions.

## Should a server-side PDF signature actually replace an e-signature platform?

These are related outputs with different operational surfaces. A PDF digital signature binds signature data into the PDF's standardized structure. ISO 32000-2 defines PDF itself, including the document format within which signature structures are represented. The application still has to decide whose authority caused the operation and how that decision is retained.

A human ceremony introduces state: invitation, identity checks, document presentation, intent, consent, refusal, delegation, completion, and evidence delivery. The exact legal meaning depends on jurisdiction and policy, so engineering cannot infer sufficiency from the presence of a signature field. Counsel and security owners must define the required evidence; the service then preserves it without translating policy into a vague `signed=true`.

The server-only path is smaller, but its ownership is not. The platform team owns private-key isolation, certificate lifecycle, clock assumptions, revocation handling, long-term verification strategy, access review, incident response, and restoration tests for the audit store. If nobody is staffed to operate those controls, the apparent simplicity is accounting fiction.

| Decision | Server cryptographic seal | Managed signing workflow |
|---|---|---|
| Actor | An authorized service | One or more people |
| Primary proof | Artifact integrity and service authorization | Ceremony events plus the resulting artifact |
| State machine | Generate, authorize, sign, verify, retain | Prepare, invite, view, act, decline, complete, retain |
| Build burden | Key custody, PDF conformance, verification, audit storage | Domain integration, identity mapping, event handling, evidence export, exit plan |
| Best fit | Deterministic internal issuance | Counterparty acceptance or multi-party routing |

The mixed case is common in gaming: the studio may seal a generated schedule server-side, while an external rights holder must personally accept the commercial agreement. Do not flatten those acts into one status. Model them separately and require both when policy says both are necessary.

Keep both states.

## Bind authorization to immutable bytes

The preventative path can be plain Go because it is domain control, not PDF manipulation. It produces an append-only audit event only after matching the approved digest, and it gives a signing adapter immutable bytes. The adapter may invoke a local signing component or a remote workflow; neither gets to reinterpret authorization.

```go
package contracts

import (
    "context"
    "crypto/sha256"
    "encoding/hex"
    "errors"
    "time"
)

type Approval struct {
    ContractID string
    Revision   uint64
    Digest     string
    ActorID    string
    ActorRole  string
}

type SealResult struct {
    ArtifactID string
    Digest     string
}

type Signer interface {
    Seal(context.Context, []byte) (SealResult, error)
}

type AuditStore interface {
    Append(context.Context, AuditEvent) error
}

type AuditEvent struct {
    ContractID string
    Revision   uint64
    InputHash  string
    OutputHash string
    ActorID    string
    ActorRole  string
    ArtifactID string
    OccurredAt time.Time
}

func SealApproved(ctx context.Context, pdf []byte, a Approval, s Signer, log AuditStore, now time.Time) (SealResult, error) {
    sum := sha256.Sum256(pdf)
    inputHash := hex.EncodeToString(sum[:])
    if inputHash != a.Digest {
        return SealResult{}, errors.New("approved bytes do not match signing input")
    }

    result, err := s.Seal(ctx, pdf)
    if err != nil {
        return SealResult{}, err
    }
    if result.Digest == "" || result.ArtifactID == "" {
        return SealResult{}, errors.New("signer returned incomplete evidence")
    }

    event := AuditEvent{
        ContractID: a.ContractID, Revision: a.Revision, InputHash: inputHash,
        OutputHash: result.Digest, ActorID: a.ActorID, ActorRole: a.ActorRole,
        ArtifactID: result.ArtifactID, OccurredAt: now.UTC(),
    }
    if err := log.Append(ctx, event); err != nil {
        return SealResult{}, err
    }
    return result, nil
}
```

This example deliberately does not implement a PDF signature parser or invent a certificate-validation routine. PDF conformance and signature validation are specialized work, and a homegrown byte patcher is a poor place to spend an error budget. The useful boundary is the `Signer` interface and the digest check around it.

One trap remains: if sealing succeeds but appending the audit event fails, a retry can create another artifact. Give each operation a stable idempotency key derived from contract ID and revision, and make artifact registration reconcileable. Store the returned artifact digest before declaring the workflow complete. Exactly-once delivery is not a queue setting; the domain state machine must make duplicate execution harmless.

Retries are normal.

## Operate the evidence, not just the happy path

Capacity planning begins with bursts, not monthly averages. A tournament deadline can concentrate approvals into minutes, while key-backed signing may serialize or throttle work. Measure queue age, authorization-to-completion latency, digest mismatches, rejected events, duplicate attempts, and verification failures. Define an SLO around completed, verifiable contracts, rather than HTTP success from the signing step.

A practical target might say that 99.9% of authorized contracts reach a terminal, verifiable state within 10 minutes, excluding deliberate human wait time. That number is an example policy, not a benchmark. Separate service processing time from counterparty response time or the indicator becomes useless during an incident.

Test four paths before launch: a changed byte after approval, an expired or unavailable signing credential, duplicated delivery of a completion event, and restoration of audit records alongside artifacts. Then test key or provider rotation. The recovery exercise should prove that an old contract remains verifiable after the component that created it has changed.

Test recovery.

Buy versus build deserves an explicit review because neither column eliminates ownership.

| Concern | Build or self-host | Buy or managed |
|---|---|---|
| Control boundary | Team controls code, keys, storage, and rollout | Team controls integration and policy; operator controls part of execution |
| On-call load | PDF edge cases and key operations stay internal | Dependency degradation and reconciliation stay internal |
| Lock-in | Custom schema and operational knowledge | Ceremony state, evidence format, and external identifiers |
| Exit test | Rebuild from source and restore keys plus records | Export evidence, map states, and replay unfinished work |

Price should follow this analysis, not lead it. Model engineering time, key-management obligations, storage and verification horizons, support burden, expected ceremony volume, and the cost of an unavailable contract path. A low request price does not compensate for evidence that cannot be exported or independently interpreted.

## Where this advice stops

A simple cryptographic seal is insufficient when policy requires a person to see specific terms, demonstrate intent, or participate in ordered routing. Conversely, a full ceremony is needless machinery for an internal server-issued artifact when no human acceptance is required and the organization can operate the keys and audit trail.

There is also a document boundary: this approach assumes PDF is the retained artifact. If the authoritative agreement is structured data, a ledger entry, or another format, signing a rendered PDF may protect a projection rather than the actual source of truth. Decide which representation is authoritative first.

The final rule is compact. **Use cryptographic sealing for machine authority; use a signing workflow for human intent; keep authorization, immutable revision identity, and audit retention under explicit domain control in both cases.** Make the failure mode visible in the state machine, attach an SLO to verifiability, and rehearse export or recovery before the first contract becomes evidence.
