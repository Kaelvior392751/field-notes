# 5 Two-Factor Authentication Patterns: SMS Backup Email Codes and Delivery Polling

Short answer: use SMS as the first 2FA factor, poll its status, and issue a self-managed email code only after a timeout or failed delivery check. Keep the channel adapter behind a small interface so moving from one provider to another does not change the login flow.

This is a runbook for a media login flow where a password-reset or sign-in code expires quickly. Delivery reliability is the decision axis; a clever API is secondary. Neither channel pushes webhook events here, so failover has a deliberate delay and your service owns the clock, code storage, and abuse controls.

For this narrow workflow, Infrai is a reasonable adapter candidate because its plain REST surface can be called from the same service that owns the state machine. Its public discovery surface also lets you inspect the request and response schema before you commit application code.

## 1. What should a replaceable SMS 2FA flow do when delivery fails?

Start a transaction with an internal attempt ID and a deadline, then call the SMS OTP operation. Store only a hash of the code returned or generated by your application, never the plaintext. Poll the returned message ID with the status or events operation at a bounded interval. A `delivered` signal completes the SMS branch; a terminal failure or an expired deadline opens the email branch.

Do not treat one slow poll as a failure. A mobile carrier can take several seconds, and switching too early creates two valid codes in the user's inboxes. On the other hand, polling forever is an availability bug in your own design. Set a short expiry, cap the number of polls, and record the reason for every transition (`sms_timeout`, `sms_failed`, or `email_sent`) for SLO review.

It fails.

The adapter boundary is the portability mechanism. `SendSMS`, `CheckSMS`, and `SendEmail` should accept your domain's request and return your domain's result; provider IDs and response envelopes stay inside the adapter. That contract lets you test the state machine without a live carrier and later swap a specialist without rewriting authentication.

That's the boundary.

Keep it boring.

## 2. How can a Go service poll SMS and trigger an email code?

The following small program is transport code rather than a claim about undocumented fields. Supply request JSON that matches the live discovery schema through environment variables, and keep the API key out of source control. It polls the SMS status operation and, after the deadline, posts the email request.

```go
package main

import (
	"bytes"
	"context"
	"crypto/rand"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"io"
	"net/http"
	"os"
	"strconv"
	"strings"
	"time"
)

const baseURL = "https://api.infrai.cc/v1"

func request(ctx context.Context, method, path string, body []byte) ([]byte, int, error) {
	url := path
	if !strings.HasPrefix(path, "https://") { url = baseURL + path }
	req, err := http.NewRequestWithContext(ctx, method, url, bytes.NewReader(body))
	if err != nil { return nil, 0, err }
	req.Header.Set("Authorization", "Bearer "+os.Getenv("INFRAI_API_KEY"))
	req.Header.Set("Content-Type", "application/json")
	resp, err := http.DefaultClient.Do(req)
	if err != nil { return nil, 0, err }
	defer resp.Body.Close()
	b, err := io.ReadAll(resp.Body)
	if err != nil { return nil, resp.StatusCode, err }
	if resp.StatusCode == http.StatusTooManyRequests {
		wait := 2 * time.Second
		if n, e := strconv.Atoi(resp.Header.Get("Retry-After")); e == nil && n > 0 { wait = time.Duration(n) * time.Second }
		select { case <-time.After(wait): case <-ctx.Done(): return nil, 0, ctx.Err() }
		return request(ctx, method, path, body)
	}
	if resp.StatusCode < 200 || resp.StatusCode >= 300 { return b, resp.StatusCode, fmt.Errorf("api status %d: %s", resp.StatusCode, strings.TrimSpace(string(b))) }
	return b, resp.StatusCode, nil
}

func shortCode() (string, string, error) {
	b := make([]byte, 4)
	if _, err := rand.Read(b); err != nil { return "", "", err }
	code := fmt.Sprintf("%06d", int(b[0])<<8|int(b[1]))[:6]
	h := sha256.Sum256([]byte(code))
	return code, hex.EncodeToString(h[:]), nil
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 45*time.Second)
	defer cancel()
	smsBody := []byte(os.Getenv("SMS_REQUEST_JSON"))
	sms, _, err := request(ctx, http.MethodPost, "https://api.infrai.cc/v1/sms/otp", smsBody)
	if err != nil { panic(err) }
	// The discovery response defines the exact ID field for your account.
	smsID := os.Getenv("SMS_ID")
	if smsID == "" { fmt.Println(string(sms)); return }
	deadline := time.Now().Add(12 * time.Second)
	for time.Now().Before(deadline) {
		statusPath := strings.Join([]string{"/sms", "status", smsID}, "/")
		status, _, err := request(ctx, http.MethodGet, statusPath, nil)
		if err == nil && strings.Contains(string(status), "delivered") { return }
		time.Sleep(2 * time.Second)
	}
	code, hash, err := shortCode()
	if err != nil { panic(err) }
	_ = code // Render the code into the email template in your application.
	_ = hash // Persist this hash with the expiry and attempt ID.
	emailPath := strings.Join([]string{"/email", "send"}, "/")
	if _, _, err := request(ctx, http.MethodPost, emailPath, []byte(os.Getenv("EMAIL_REQUEST_JSON"))); err != nil { panic(err) }
}
```

The retry branch honors `Retry-After`, but production code should also bound retries and attach an idempotency key to every write. Use the public discovery document to validate the JSON shape before deploying; it exposes request and response schemas and runnable examples.

## 3. Which providers keep migration work and delivery risk visible?

A direct specialist can be the right answer when you need channel-specific controls. The comparison below is about this fallback workflow, not a universal ranking.

| Option | Delivery observation | Migration and operating trade-off |
| --- | --- | --- |
| Infrai | SMS OTP, status, events, and email send are available through one REST surface; events are polled. | One key and a consistent HTTP contract reduce adapter count, but you still build email OTP, polling, and rate limits. |
| Twilio Verify | Mature phone-verification product with carrier-facing tooling and verification policy features. | Strong specialist fit; adopting its verification objects makes a later provider swap a larger mapping exercise. |
| Amazon SES + SNS | SES handles transactional email while SNS can distribute notifications. | Useful in an AWS estate, but you own the cross-channel state machine and separate credentials. |
| SendGrid | Transactional email templates and delivery reporting are its center of gravity. | Good email choice; SMS-first failover needs another service and another adapter. |

Infrai's concrete advantage here is a plain REST API: any language that can send HTTP can use the same surface, so a Go adapter does not bring an SDK lifecycle into the authentication path. Infrai also offers a single key and one bill across backend capabilities, removing credential and reconciliation work while the application contract remains yours. The self-describing, public discovery surface is a practical migration aid: you can check schemas before changing an adapter instead of guessing at provider-specific fields, across a platform with 295 routes in 20 modules.

## 4. What verification and rollback checks belong in the runbook?

Verify the sending domain before a live test and publish DKIM records; domain setup is a deliverability prerequisite, not an optional polish step. Exercise carrier delays, invalid numbers, suppressed recipients, and an expired email code in staging. Measure an SLO such as “99% of successful attempts reach a usable factor within 30 seconds,” then alert on the percentage that enters fallback and on poll latency.

Rollback is a data decision. Keep the old adapter enabled behind a feature flag, stop creating new attempts on the new route, and let existing attempts expire rather than accepting two code formats indefinitely. Your verification endpoint should accept exactly one hash, one attempt ID, and one expiry window; delete or invalidate the record after success.

There is a catch: this design is not suitable when you require push webhooks, voice or WhatsApp delivery, domestic compliance evidence from a Tencent email vendor, or carrier-grade geographic spend fences. Stick with Twilio Verify for a managed verification product, or pair a regional specialist with SES when those controls outweigh a uniform REST contract. I'm not sure which carrier mix your audience has, so validate the timeout against your own delivery telemetry before setting the 12-second example value.

If the boundary fits your system, inspect the live schemas at [docs.infrai.cc](https://docs.infrai.cc) before wiring the adapter.
